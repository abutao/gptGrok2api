# 日志与图片一键清除设计

## 目标

在管理后台的“日志管理”和“图片管理”页面分别提供独立的“一键清除”操作，供管理员一次性清理对应资源，同时避免触碰账号、配置、任务和视频数据。

## 范围与行为

### 日志管理

- 新增管理员专用清除接口，不复用按 ID 删除接口。
- 清除调用日志 `data/logs.jsonl`。
- 清除运行日志文件：
  - `data/runtime.log`
  - `data/app.log`
  - `logs/runtime.log`
  - `logs/app.log`
- 文件不存在视为已清除，不报错。
- 返回清除的文件数、日志条目数（调用日志可统计 JSONL 条目，运行日志按非空行统计）和释放字节数。
- 不清除内存中的实时监控任务状态；清除后新产生的日志仍正常写入。

### 图片管理

- 新增管理员专用清除接口，不复用普通按路径删除接口。
- 递归清除 `ImageDataDir` 下所有受支持的图片文件及对应 `.meta.json` 文件。
- 删除图片标签文件 `data/image_tags.json`，实现彻底清理。
- 清理图片目录中的空目录，但保留图片根目录本身。
- 不删除视频目录、账号、配置、任务队列或其他数据文件。
- 返回图片文件数、元数据文件数、释放字节数和标签文件是否删除。

## API 设计

- `POST /api/logs/clear`
  - 需要管理员认证。
  - 空请求体即可。
  - 返回 `{ ok, files, entries, freed_bytes }`。
- `POST /api/images/clear`
  - 需要管理员认证。
  - 空请求体即可。
  - 返回 `{ ok, media_files, metadata_files, freed_bytes, tags_file_removed }`。
- 两个接口均限制为 POST；其他方法返回 405。
- 删除过程遇到单个文件失败时返回 500，并包含可诊断错误；不会通过用户输入拼接路径，因此不存在路径穿越参数面。

## 前端交互

- 日志页面增加“清除全部日志”按钮。
  - 调用前使用统一确认弹窗，明确提示会同时清除调用日志和运行日志。
  - 成功后刷新当前日志视图和统计，并提示清除结果。
- 图片页面增加“清除全部图片”按钮。
  - 调用前使用统一确认弹窗，明确提示图片、元数据和标签都会永久删除。
  - 成功后清空当前选择、关闭失效的预览/标签编辑状态，刷新图库和存储统计，并提示释放空间。
- 清除期间按钮禁用，避免重复提交。
- 接口失败时保留页面内容并显示错误提示。

## 并发与安全

- 日志清除与日志追加共用现有 `Server.logMu`，避免清空与追加交错导致数据恢复或写入覆盖。
- 标签文件操作继续使用现有 `imageTagsMu`。
- 图片清除只操作配置解析出的图片根目录，并复用已有图片扩展名判断和空目录清理逻辑。
- 清除接口始终执行管理员权限校验。

## 测试与验证

后端先以临时目录测试两个清除接口：

1. 日志清除删除调用日志和所有运行日志，并返回正确计数；不存在文件时仍成功。
2. 图片清除删除嵌套图片、元数据和标签文件，保留根目录及非图片数据。
3. 非 POST 请求被拒绝，未认证请求不能清除。

前端执行 `npm run build`；Go 侧执行相关 `go test`、`go build ./cmd/gptgrok2api` 和 `go vet ./internal/...`。既有无关失败单独记录，不扩大本次范围。
